# Техническое задание: сервис генерации изображений на базе внешних ИИ-провайдеров

Документ предназначен для загрузки в кодового агента. Содержит архитектуру, контракты,
модель данных и правила, нарушать которые нельзя. Схемы БД лежат в файлах
`billing.prisma` и `generation.prisma`, инфраструктура — в `docker-compose.yml` и `.env.example`.

---

## 1. Суть проекта

Веб-сервис генерации и редактирования изображений для российского рынка.
Модели не хостим — обращаемся к внешним провайдерам через API.
Зарабатываем на разнице между себестоимостью генерации и ценой для пользователя.

Каналы: сайт (основной), Telegram-бот, позже — собственное API для B2B.
Целевая аудитория первого этапа: бизнес и селлеры маркетплейсов, контент для товаров и соцсетей.

Провайдеры генерации: **kie.ai** (основной по изображениям), **OpenRouter** (текстовый
ИИ-консультант), **GenAPI** (резерв). Оплата провайдерам идёт со счетов владельца сервиса,
пользователь платит сервису в рублях.

---

## 2. Принципы, которые нельзя нарушать

Эти правила важнее любых оптимизаций. При конфликте требований — выигрывают они.

1. **Баланс существует только в биллинге.** Контур генераций баланс не хранит и не считает.
2. **Ни одна генерация не запускается без подтверждённого резерва кредитов.**
3. **Каждая операция с деньгами идемпотентна.** Повтор запроса не создаёт вторую запись.
4. **Ошибка генерации возвращает кредиты автоматически.** Пользователь не платит за брак.
5. **Туннель никогда не является маршрутом по умолчанию.** Через egress ходят только
   адаптеры внешних провайдеров, всё остальное — напрямую.
6. **Результат забирается в своё S3 сразу.** Ссылки провайдеров живут часы, полагаться на них нельзя.
7. **Себестоимость фиксируется в момент завершения генерации** в трёх полях: USD, курс, рубли.
8. **Деньги — целые числа.** Копейки и кредиты в `Int`, никаких чисел с плавающей точкой.
9. **Лимиты расхода на пользователя проверяются до постановки задачи**, а не после.

## 3. Архитектура

Система делится на два независимых контура. Это сделано намеренно: падение генераций
не должно останавливать приём денег.

### Платёжный контур

Работает с прямым выходом в сеть, без туннеля. Наружу ходит только в кассы.

- **web** — публичный сайт, лендинг, тарифы, оформление оплаты
- **billing** — сервис-источник истины: аккаунты, баланс, холды, транзакции, платежи, подписки

### Контур генераций

Кабинет доступен снаружи напрямую. К провайдерам ходит только через egress.

- **app** — личный кабинет: генерации, история, проекты, консультант
- **worker** — очередь генераций, ретраи, фолбэки, забор файлов в S3
- **bot** — Telegram-бот
- **egress** — контейнер с VPN-клиентом, отдаёт HTTP-прокси внутрь сети

### Связь между контурами

Единственный канал — внутренний API биллинга, вызываемый контуром генераций.
Наружу этот API не публикуется. Никаких внешних ключей между базами:
`userId` в контуре генераций — обычный UUID без ссылочной целостности.

```
ЮKassa / Т-Банк                          kie.ai / OpenRouter / GenAPI
      |                                              ^
      v                                              |
+--------------------+                    +----------------------+
| ПЛАТЁЖНЫЙ КОНТУР   |                    | КОНТУР ГЕНЕРАЦИЙ     |
|  web (сайт, касса) |                    |  egress (VPN+proxy)  |
|  billing (баланс)  | <----------------- |  app (кабинет)       |
+--------------------+   резерв/списание  |  worker, bot         |
                                          +----------------------+
```

## 4. Инфраструктура

Хостинг: **Timeweb Cloud**, российская локация.
Первый этап — один VPS, ориентир 4 vCPU / 8 ГБ RAM / 160 ГБ NVMe.
Хранилище файлов — S3 Timeweb, отдельным бакетом. На диск VPS результаты не пишем.

Все сервисы поднимаются через Docker Compose. Две docker-сети:

- `web` — сервисы, которым нужен прямой выход и входящие соединения
- `internal` — межсервисное взаимодействие и доступ к egress

Контейнеры `billing` и `postgres` не имеют публичных портов вообще.

### Egress

Отдельный контейнер: WireGuard-клиент плюс HTTP-прокси (tinyproxy или аналог),
слушающий только во внутренней сети. Требует `cap_add: NET_ADMIN`.

Обязательно:
- healthcheck, проверяющий доступность провайдера через туннель
- DNS-резолв доменов провайдеров идёт через туннель
- при падении egress статус пишется в таблицу `ProviderState`, воркер переводит задачи в отложенные

**Важно:** прокси используется точечно, на уровне HTTP-клиента конкретного адаптера.
`setGlobalDispatcher` запрещён — глобальная подмена диспетчера утащит в туннель
запросы к кассам и Telegram.

```ts
import { ProxyAgent, request } from 'undici';

const tunnel = new ProxyAgent(process.env.EGRESS_PROXY_URL!);

// адаптеры kie.ai / OpenRouter / GenAPI
await request(url, { dispatcher: tunnel, method: 'POST', body });

// ЮKassa, Т-Банк, Telegram, S3 — без dispatcher
```

## 7. Модель данных

Схемы целиком — в `billing.prisma` и `generation.prisma`. Ключевое:

**Биллинг:** `User`, `Wallet`, `Hold`, `Transaction`, `Payment`, `PaymentWebhook`,
`Plan`, `Subscription`, `ApiKey`, `AuditLog`.

**Генерации:** `Profile`, `Project`, `BrandKit`, `Model`, `Preset`, `Generation`,
`Output`, `Moderation`, `ProviderState`, `FxRate`, `ChatSession`, `UsageDaily`, `GuestQuota`.

Два инварианта, которые нужно проверять ночным заданием:

- `Wallet.credits` равен сумме `Transaction.credits` по пользователю
- `Wallet.heldCredits` равен сумме кредитов по холдам в статусе `ACTIVE`

Расхождение — критический алерт.

## 8. Контракт внутреннего API биллинга

Базовый путь `/internal/v1`. Доступен только из сети `internal`.
Авторизация — заголовок `X-Service-Token` плюс HMAC-подпись тела в `X-Signature`.

Все ручки принимают `idempotencyKey`. Повторный вызов с тем же ключом
возвращает результат первой операции с кодом 200, а не создаёт новую запись.

### POST /internal/v1/holds — зарезервировать кредиты

```jsonc
// запрос
{ "userId": "uuid", "credits": 5, "idempotencyKey": "gen_abc123", "externalRef": "generationId", "ttlSec": 900 }

// 200
{ "holdId": "uuid", "credits": 5, "balanceAfter": 120, "expiresAt": "..." }

// 409 — недостаточно средств
{ "error": "INSUFFICIENT_FUNDS", "available": 3, "required": 5 }
```

### POST /internal/v1/holds/:holdId/commit — подтвердить списание

Вызывается после успешной генерации. Создаёт транзакцию `SPEND`,
уменьшает `heldCredits`. Повторный вызов идемпотентен.

### POST /internal/v1/holds/:holdId/release — вернуть резерв

Вызывается при ошибке, отмене или таймауте. Кредиты возвращаются в доступные.

### GET /internal/v1/users/:userId/balance

Только для отображения. Решение о запуске генерации принимается по ответу
на создание холда, а не по этой ручке.

### Обработка таймаутов

Если вызов `holds` завис и ответ не получен, воркер обязан повторить запрос
**с тем же ключом идемпотентности**. Создание второго холда недопустимо.
Холды с истёкшим `expiresAt` освобождаются фоновым заданием каждые 5 минут.

### Вебхук биллинг → контур генераций

`POST /internal/v1/profile-sync` — при смене тарифа биллинг уведомляет кабинет,
тот обновляет `Profile.planCode` и производные ограничения.

## 9. Адаптеры провайдеров

Единый интерфейс. Код приложения не знает, какой провайдер используется.
Маршрут задаётся строкой в таблице `Model`, смена провайдера не требует деплоя.

```ts
export interface GenerationRequest {
  providerModelId: string;
  prompt: string;
  params: Record<string, unknown>;
  inputFiles?: { url: string; role: string }[];
  callbackUrl?: string;
  idempotencyKey: string;
}

export interface GenerationResult {
  providerTaskId: string;
  status: 'processing' | 'success' | 'error';
  outputs?: { url: string; mimeType: string; width?: number; height?: number }[];
  costUsd?: number;
  errorCode?: string;
  errorMessage?: string;
}

export interface ProviderAdapter {
  readonly name: 'KIE' | 'OPENROUTER' | 'GENAPI';
  submit(req: GenerationRequest): Promise<GenerationResult>;
  poll(providerTaskId: string): Promise<GenerationResult>;
  parseCallback(body: unknown, headers: Record<string, string>): GenerationResult;
  getBalance(): Promise<{ balanceUsd: number } | null>;
}
```

Требования к каждому адаптеру:

- все запросы идут через `EGRESS_PROXY_URL`
- таймаут из `Model.timeoutSec`, по истечении — задача в ошибку с возвратом кредитов
- ретраи только на сетевых ошибках и 5xx, максимум 2 попытки, экспоненциальная пауза
- 4xx не ретраится — это ошибка запроса, задача сразу в `ERROR`
- себестоимость пишется в `costUsd` из ответа провайдера; если провайдер не отдаёт —
  берётся `Model.expectedCostUsd` и помечается флагом в `meta`

**Колбэки от провайдеров** приходят на публичный домен кабинета напрямую, туннель
для входящих не нужен. Полагаться только на колбэки нельзя: параллельно работает
поллинг статуса для задач, висящих в `PROCESSING` дольше трети таймаута.

## 10. Жизненный цикл генерации

```
1. Кабинет принимает запрос, валидирует, применяет модерацию промпта
2. Проверка лимитов пользователя (Redis: дневной расход, конкурентность, рейт-лимит)
3. Проверка ProviderState: провайдер доступен, баланс не низкий, egress жив
4. Создание Generation в статусе PENDING с idempotencyKey
5. POST /holds в биллинг → holdId
6. Постановка задачи в BullMQ с приоритетом из Profile.queuePriority
7. Worker: submit к провайдеру через egress → PROCESSING
8. Колбэк или поллинг → результат
9a. Успех: файлы забираются в S3, создаются Output, считается costRub,
    вызывается /commit, статус SUCCESS
9b. Ошибка: попытка фолбэка на Model.fallbackProvider (новая Generation с isFallback)
    Если фолбэк не помог — /release, статус ERROR, кредиты у пользователя
10. Уведомление в интерфейс (SSE или поллинг) и в Telegram, если пользователь связал аккаунт
```

Отдельно: при падении egress задачи не ретраятся вхолостую, а переводятся
в отложенные с показом пользователю честного статуса «сервис временно недоступен,
кредиты не списаны».

## 11. Платежи

Провайдеры: ЮKassa и Т-Банк (СБП). Реализуются как отдельные адаптеры за общим интерфейсом.

Порядок:

1. Пользователь выбирает пакет кредитов или тариф
2. Создаётся `Payment` в статусе `PENDING` со своим `idempotencyKey`
3. Редирект на страницу оплаты провайдера
4. Приходит вебхук

Обработка вебхука обязательно в таком порядке:

1. Проверка подписи и IP отправителя
2. Запись сырого события в `PaymentWebhook` **до** обработки
3. Проверка `providerPaymentId` на уникальность — повторное событие не начисляет кредиты дважды
4. В одной транзакции: обновление `Payment`, создание `Transaction` типа `TOPUP`,
   инкремент `Wallet.credits`
5. Ответ 200 провайдеру

Если обработчик упал после шага 2 — событие переигрывается фоновым заданием из `PaymentWebhook`.

Подписки: автопродление фоновым заданием по `Subscription.currentPeriodEnd`,
списание сохранённым методом оплаты. Неудача — статус `PAST_DUE`, три попытки,
затем `EXPIRED` и понижение до бесплатного тарифа.

## 12. Тарифы и кредиты

Кредит — внутренняя единица. Цена модели в кредитах задаётся в `Model.priceCredits`.

Расчёт цены: `priceCredits = expectedCostUsd * курс * наценка / стоимость_кредита`.
Целевая наценка: 3–5x на массовых моделях, 2–2,5x на видео. В наценку закладывается
запас 10–15% на движение курса — закупка в валюте, продажа в рублях.

Стартовая сетка (задаётся данными, не кодом):

| Тариф | Цена | Что даёт |
|---|---|---|
| FREE | 0 | 10 кредитов при регистрации, вотермарк, низкое разрешение, только дешёвые модели |
| START | 690 ₽/мес | кредиты по тарифу, без вотермарка, полное разрешение |
| PRO | 1490 ₽/мес | приоритет очереди, пакетный режим, премиум-модели, брендкит |
| BUSINESS | от 9900 ₽/мес | команды, API-ключ, закрывающие документы |

Пакеты кредитов без срока сгорания: 299 / 799 / 1990 ₽.

## 13. Лимиты и защита бюджета

Владелец оплачивает провайдеров вперёд, поэтому защита обязательна в первой версии.

**Лимиты пользователя** (счётчики в Redis, дневной итог в `UsageDaily`):
- дневной потолок расхода в кредитах по тарифу
- конкурентные задачи: `Profile.concurrentJobs`
- рейт-лимит на постановку задач и на сообщения консультанту

**Гости до регистрации:** 2 генерации по `GuestQuota`, ключ — отпечаток браузера,
дополнительный лимит по IP. Дешёвая модель, низкое разрешение, вотермарк.

**Контроль провайдеров:** фоновое задание раз в 10 минут опрашивает балансы,
пишет в `ProviderState`. При падении ниже порога — уведомление владельцу в Telegram,
при исчерпании — автоматическое переключение на резервного провайдера,
при недоступности всех — мягкое отключение платных генераций с внятным сообщением.

**Контроль маржи:** ежедневный отчёт сравнивает `Generation.costUsd` с
`Model.expectedCostUsd`. Отклонение больше 20% — алерт, значит провайдер изменил цены.

## 14. Модерация

Три стадии, результат пишется в `Moderation`:

1. **Промпт** — стоп-слова и классификатор до отправки провайдеру
2. **Входное изображение** — проверка загрузок
3. **Результат** — выборочная проверка вывода

Блокируется: сексуальный контент, насилие, генерация узнаваемых реальных людей
и публичных персон, материалы с участием несовершеннолетних. При вердикте `BLOCK`
задача не отправляется провайдеру, кредиты не списываются, пользователю показывается
причина без раскрытия правил фильтра.

---

## 15. ИИ-консультант

Роль — не поддержка, а интерфейс. Убирает необходимость уметь писать промпты.

Функции:
- принимает задачу на естественном языке, собирает промпт, выбирает модель из каталога,
  выставляет размер и запускает генерацию
- правки итерациями: «фон светлее», «сделай вертикально» — без переписывания промпта
- подсказывает форматы под площадки
- предупреждает, когда кредитов не хватит на задуманное

Реализация: OpenRouter, дешёвая модель, вызовы через egress.
Диалог хранится в `ChatSession` / `ChatMessage` с учётом токенов и стоимости.
Бесплатным пользователям — 10–15 сообщений, дальше по тарифу.

Консультант запускает генерацию через тот же путь, что и обычный интерфейс:
резерв кредитов, очередь, подтверждение. Обходных путей нет.

## 16. Хранилище

S3 Timeweb. Структура ключей: `{userId}/{generationId}/{outputId}.{ext}`.

Файл забирается у провайдера сразу по колбэку, до отдачи пользователю.
Пользователю выдаются подписанные ссылки с коротким временем жизни.

Политика хранения: бесплатный тариф — 7 дней, платные — бессрочно.
Удаление фоновым заданием по `Output.deletedAt`.

## 17. Наблюдаемость

Логи JSON с `traceId`, сквозным через все сервисы, включая вызовы биллинга.

Метрики, которые нужны с первого дня:
- очередь: длина, время ожидания, доля ошибок по провайдерам
- деньги: расход в USD за сутки, выручка в рублях, маржа по моделям
- балансы провайдеров и статус egress
- воронка: регистрации, первая генерация, первая оплата

Алерты владельцу в Telegram: падение egress, низкий баланс провайдера,
доля ошибок выше 10% за 15 минут, расхождение баланса при ночной сверке,
неудачная обработка вебхука кассы.

## 18. Безопасность

- Внутренний API биллинга не публикуется наружу, только сеть `internal`
- Подпись межсервисных запросов, ротация `SERVICE_TOKEN`
- Проверка подписи и IP на вебхуках касс
- Валидация всех внешних входов через Zod
- Пароли — argon2, API-ключи хранятся только хэшем
- Секреты только в переменных окружения, в репозитории — `.env.example`
- Загрузки: проверка MIME, лимит размера, антивирусная проверка, отдача только через подписанные ссылки

**Публичный сайт (`web`):**
главная с полем промпта и пресетами, страницы инструментов под SEO (по одной на задачу),
тарифы, оплата, оферта и политика, публичная галерея.

**Кабинет (`app`):**
рабочая зона генерации, чат с консультантом, история и избранное, проекты и брендкит,
пакетный режим, баланс и тариф, реферальная ссылка, API-ключи.

Дизайн: тёмная тема по умолчанию, один акцентный цвет, без градиентов.
Стоимость в кредитах показывается **до** запуска. Прогресс честный:
очередь → генерация → готово, с оценкой времени. Мобильная версия обязательна.

## 20. Этапы

**Этап 1 — каркас.** Docker Compose, egress с проверкой туннеля, две базы,
биллинг с холдами и транзакциями, адаптер kie.ai, одна модель, генерация из кабинета.
Критерий приёмки: генерация проходит полный цикл, при выключенном туннеле
кредиты возвращаются автоматически.

**Этап 2 — деньги.** ЮKassa и Т-Банк, вебхуки с идемпотентностью, пакеты и тарифы,
лимиты и гостевые квоты, ночная сверка балансов.

**Этап 3 — продукт.** Каталог моделей с фолбэками, пресеты, история и S3,
модерация, консультант на OpenRouter.

**Этап 4 — каналы.** Telegram-бот со сквозным балансом, SEO-страницы инструментов,
реферальная программа.

**Этап 5 — B2B.** Пакетный режим, брендкит, API-ключи, закрывающие документы.

## 21. Что запрещено делать

- Дублировать баланс в контуре генераций
- Использовать `setGlobalDispatcher` или заворачивать весь трафик в туннель
- Запускать генерацию до подтверждения резерва
- Отдавать пользователю прямые ссылки провайдеров
- Хранить результаты на диске VPS
- Начислять кредиты по вебхуку без проверки подписи и уникальности платежа
- Использовать числа с плавающей точкой для денег и кредитов
- Создавать внешние ключи между базами двух контуров
