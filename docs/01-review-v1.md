# Ревизия ТЗ v1: дефекты, которые нужно закрыть до кода

Документ фиксирует, что именно в исходном ТЗ ломается на продакшене, почему и как чинится.
Каждый пункт — либо потеря денег, либо дыра в безопасности, либо ложный алерт,
либо обещание в тексте, не подкреплённое инфраструктурой.

Порядок — по стоимости ошибки, а не по разделам исходного документа.

---

## Блок A. Деньги и учёт

### A1. Инвариант ночной сверки записан неверно — критический алерт будет срабатывать каждую ночь

**Было (§7):** `Wallet.credits` равен сумме `Transaction.credits` по пользователю.

**Почему ломается.** Холд уменьшает `credits` и увеличивает `heldCredits`, но транзакции
не создаёт — транзакция `SPEND` появляется только на коммите. Значит при любом активном
холде равенство нарушено по построению.

```
TOPUP +100         → credits=100 held=0   Σtx=100   ✔
HOLD 5             → credits=95  held=5   Σtx=100   ✘ (95 ≠ 100)
COMMIT (SPEND -5)  → credits=95  held=0   Σtx=95    ✔
```

**Стало.** Два инварианта, оба проверяются ночью и оба должны выполняться в любой момент:

```
I1: Wallet.credits + Wallet.heldCredits == Σ Transaction.credits (по пользователю)
I2: Wallet.heldCredits              == Σ Hold.credits WHERE status = ACTIVE
I3: Transaction.balanceAfter последней транзакции == Wallet.credits + Wallet.heldCredits
```

### A2. Резерв кредитов написан как read-modify-write — двойная трата при параллельных запросах

**Было.** В `Wallet` есть поле `version` «оптимистичная блокировка», но контракт `POST /holds`
не описывает, как именно списывается баланс. Кодовый агент напишет `SELECT` → проверка →
`UPDATE`. При пакетном запуске (20 генераций разом, два таба, ретрай) пользователь уйдёт в минус.

**Стало.** Ровно один атомарный условный `UPDATE`, никакого предварительного чтения:

```sql
UPDATE "Wallet"
   SET credits       = credits - $credits,
       "heldCredits" = "heldCredits" + $credits,
       version       = version + 1,
       "updatedAt"   = now()
 WHERE "userId" = $userId
   AND credits >= $credits
RETURNING credits, "heldCredits", version;
```

Ноль изменённых строк → `409 INSUFFICIENT_FUNDS`. `balanceAfter` для транзакции берётся
из `RETURNING`, а не отдельным запросом. Оптимистичная блокировка через `version` остаётся
только для админских правок, где нужна проверка «никто не менял с момента показа формы».

### A3. Идемпотентность описана наполовину

**Было (§8):** «повторный вызов с тем же ключом возвращает результат первой операции с кодом 200».
Не описаны два случая, которые обязательно случатся:

1. Первый запрос ещё **в полёте**, приходит второй с тем же ключом. Оба видят «записи нет»,
   оба вставляют → один падает на уникальном индексе с 500-й ошибкой.
2. Тот же ключ пришёл **с другим телом** (баг клиента, переиспользование ключа).
   Вернуть результат первой операции — значит молча соврать вызывающему.

**Стало.** Таблица `IdempotencyRecord (scope, key, requestHash, state, statusCode, responseJson)`,
уникальность по `(scope, key)`. Протокол:

| Ситуация | Ответ |
|---|---|
| Ключа нет | вставка `IN_PROGRESS`, выполнение, запись `DONE` + снимок ответа |
| Ключ есть, `DONE`, тот же `requestHash` | снимок ответа, тот же код, заголовок `Idempotent-Replay: true` |
| Ключ есть, `IN_PROGRESS` | `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1` |
| Ключ есть, `requestHash` другой | `422 IDEMPOTENCY_KEY_REUSE` |

### A4. Ключи идемпотентности уникальны глобально, а не в пределах пользователя

`Hold.idempotencyKey String @unique`, `Generation.idempotencyKey String @unique`,
`Transaction.idempotencyKey String? @unique`. Если ключ хоть частично приходит от клиента,
пользователь A может занять ключ пользователя B, и запрос B вернёт чужой результат
или упадёт. **Стало:** `@@unique([userId, idempotencyKey])` + обязательный префикс области
(`gen:`, `topup:`, `sub:`), клиентский идентификатор принимается отдельным полем
`clientRequestId` и никогда не используется как ключ напрямую.

### A5. Фолбэк создаёт второй холд — пользователь платит дважды или не получает фолбэк вовсе

**Было (§10, 9b):** «попытка фолбэка на `Model.fallbackProvider` (новая `Generation` с `isFallback`)».
Новая генерация → новый `POST /holds`, при том что холд родителя ещё `ACTIVE`.
У пользователя с 5 кредитами фолбэк не запустится — денег «нет».

**Стало.** Фолбэк — та же логическая операция. Дочерняя `Generation` наследует `holdId`
родителя и **не создаёт** нового резерва. Если фолбэк-модель дороже основной — разницу
несёт сервис; пользователь платит по цене модели, которую выбрал. Коммит делает та ветка,
которая завершилась успехом, ровно один раз (защита — `Hold.status` переходит из `ACTIVE`
только один раз, повторный коммит идемпотентен).

### A6. Не определён коммит просроченного холда

Фоновое задание освобождает холды каждые 5 минут. Генерация видео завершилась на 16-й минуте
при `HOLD_TTL_SEC=900`. Воркер зовёт `/commit` на холде в статусе `EXPIRED`. Что делать —
не написано; кодовый агент вернёт 409 и сервис отдаст платный результат бесплатно.

**Стало.**
* TTL холда задаётся правилом, а не константой: `ttlSec = model.timeoutSec * (maxAttempts + 1) + 300`,
  минимум 900, и обязательно больше самого долгого таймаута в каталоге.
* Переход `EXPIRED → COMMITTED` разрешён. Если после освобождения средств не хватает —
  создаётся `SPEND` с уходом баланса в минус (флаг `allowNegative` только для этого случая),
  пишется `AuditLog` и алерт. Отдать результат и остаться с отрицательным балансом дешевле,
  чем раздавать генерации бесплатно.
* Освобождение просроченных холдов идёт только по тем, где `externalRef`-генерация уже
  в терминальном статусе или старше TTL, — иначе воркер и джоба гоняются за одним холдом.

### A7. `PaymentWebhook.@@unique([provider, eventId])` не защищает от дублей

`eventId String?` — nullable. В PostgreSQL `NULL` не конфликтует с `NULL`, поэтому
уникальный индекс не сработает ни на одном событии без явного идентификатора.
А §11 прямо требует защиты от повторного начисления.

**Стало.** Поле `eventKey String` (NOT NULL) = идентификатор события провайдера,
а при его отсутствии — `sha256(raw_body)`. Уникальность по `(provider, eventKey)`.
Второй рубеж — уникальность `Payment.providerPaymentId` и проверка перехода статуса.

### A8. `Payment.providerPaymentId` не может быть NOT NULL

Платёж создаётся в статусе `PENDING` **до** обращения в кассу — идентификатора кассы
в этот момент ещё нет. Схема требует значение. **Стало:** `String?` с `@unique`
(уникальность в PostgreSQL допускает несколько NULL — здесь это как раз нужно).

### A9. Возвраты поддержаны только целиком

Есть `PaymentStatus.REFUNDED` и `Payment.refundedAt`, но частичный возврат
(вернули 500 ₽ из 1990 ₽) записать некуда, а он неизбежен при спорах и чарджбэках.
**Стало:** отдельная модель `Refund` со своим `providerRefundId`, суммой, причиной
и связью с транзакцией списания кредитов.

### A10. Кредиты «без срока сгорания» — бессрочное обязательство

§12 обещает пакеты без сгорания. С точки зрения учёта это вечный аванс в пассиве,
с точки зрения продукта — накопленный «долг», который однажды предъявят разом.
**Стало:** сгорание при 12 месяцах полного бездействия, с уведомлением за 30 и за 7 дней,
пункт в оферте, тип транзакции `EXPIRE` уже есть в схеме. Формулировка для витрины —
«кредиты не сгорают, пока вы пользуетесь сервисом».

## Блок B. Безопасность

### B1. Внутренний API биллинга фактически опубликован наружу

Текст (§3, §8, §18) обещает: «наружу этот API не публикуется», «доступен только из сети internal».
Инфраструктура это не обеспечивает:

```yaml
billing:
  networks: [web, internal]      # ← в сети web
caddy:
  depends_on: [site, cabinet, billing]   # ← Caddy к нему ходит
```

Контейнер слушает один порт на всех интерфейсах. Как только в `Caddyfile` появится
`reverse_proxy billing:3000` для вебхуков касс — вместе с `/webhooks/*` наружу уедет
и `/internal/v1/*`. Остаётся только `X-Service-Token`, то есть один секрет между
интернетом и балансами всех пользователей.

**Стало.** Один образ, два процесса с разными ролями:

| Контейнер | Сети | Слушает | Отдаёт |
|---|---|---|---|
| `billing-public` | `edge`, `internal` | `:3000` | `/webhooks/*`, `/auth/*`, `/api/public/*` |
| `billing-internal` | `internal` | `:3100` | `/internal/v1/*` |

Caddy знает только про `billing-public`. Внутренний API физически не имеет маршрута
из интернета. В `Caddyfile` дополнительно явный `respond /internal/* 404` как второй рубеж,
в приложении — проверка, что запрос к `/internal/*` пришёл на internal-листенер.

### B2. Колбэки провайдеров ничем не аутентифицированы

§9: «колбэки от провайдеров приходят на публичный домен кабинета напрямую».
Про подпись, токен и защиту от подделки — ни слова. Любой, кто узнает формат,
шлёт `{"status":"success"}` и получает коммит холда без реальной генерации.
А `costUsd` из тела уедет прямиком в отчёт о марже.

**Стало.**
* URL колбэка содержит одноразовый токен: `/api/callbacks/{provider}/{generationId}/{token}`,
  где `token = HMAC(secret, generationId)`, сравнение — константное по времени.
* Где провайдер умеет подписывать тело — подпись проверяется обязательно.
* Тело колбэка **не является источником истины**: успех и `costUsd` подтверждаются
  поллингом `poll(providerTaskId)`. Колбэк — только сигнал «пора спросить».
* Сырое событие пишется в `ProviderCallback` до обработки (симметрично `PaymentWebhook`),
  обработчик отвечает 200 за миллисекунды и ставит задачу в очередь.
* Статус-автомат монотонный: `PROCESSING` после `SUCCESS` игнорируется.

### B3. Ретрай `submit` при сетевом таймауте оплачивается дважды

§9: «ретраи только на сетевых ошибках и 5xx, максимум 2 попытки». Сетевой таймаут на
`submit` не означает, что провайдер не принял задачу — чаще означает обратное.
Две попытки = два платных задания у провайдера, из них одно осиротевшее.

**Стало.** `submit` **не ретраится вслепую**. При таймауте/обрыве генерация переходит
в `SUBMIT_UNKNOWN`, и дальше — реконсиляция: поиск задачи у провайдера по нашему
`idempotencyKey` (там, где провайдер это поддерживает — флаг `Model.supportsIdempotency`),
иначе ожидание колбэка до `timeoutSec`. Только после подтверждённого «задачи нет»
разрешён повтор. Ретраи как были — для `poll`, `getBalance` и 5xx на неидемпотентных ручках.

### B4. Забор файла у провайдера — готовый SSRF

Воркер скачивает URL, пришедший снаружи. Ничто не мешает провайдеру (или тому, кто
подделал колбэк, см. B2) вернуть `http://169.254.169.254/...` или `http://billing:3000/internal/v1/...`.

**Стало:** только `https`, резолв имени и проверка итогового IP против приватных диапазонов
(RFC1918, loopback, link-local, CGNAT, IPv6 ULA), не более 3 редиректов с повторной проверкой
на каждом, лимит размера и времени, сверка `Content-Type` с ожидаемым, загрузка через egress.

### B5. `AuthSession.refreshToken` хранится в открытом виде

Пароли — argon2, ключи API — только хэш, а refresh-токен лежит как есть. Утечка дампа =
захват всех живых сессий. **Стало:** `refreshTokenHash` (SHA-256 достаточно: токен и так
высокоэнтропийный), ротация при каждом обновлении, инвалидация всей цепочки при повторном
использовании старого токена.

### B6. Гостевая квота по отпечатку браузера обходится за две секунды

`GuestQuota.fingerprint @unique`, 2 бесплатные генерации. Инкогнито-окно, смена
user-agent, любой антидетект — и лимит обнуляется. При платной генерации это прямой слив бюджета.

**Стало, послойно:** капча (Yandex SmartCaptcha) перед первой гостевой генерацией →
лимит по IP и по подсети /24 и по ASN → только самая дешёвая модель с вотермарком и
низким разрешением → **глобальный дневной потолок расходов на гостей в USD** с автоматическим
отключением гостевого режима при исчерпании. Плюс очистка таблицы: сейчас она растёт вечно.

### B7. Антивирус заявлен, но его нет

§18 требует антивирусную проверку загрузок. В `docker-compose.yml` такого сервиса нет.
**Стало:** контейнер `clamav` в профиле, проверка до помещения в S3; плюс то, о чём ТЗ
не упоминает вовсе — защита от «архивных бомб» изображений: лимит на пиксели
(не только на байты), обязательное перекодирование через sharp, снятие EXIF
(в том числе GPS-координат пользователя).

## Блок C. Инфраструктура и эксплуатация

### C1. «Два независимых контура» стоят на одном Postgres и одном Redis

Смысл разделения (§3) — «падение генераций не должно останавливать приём денег».
Фактически обе базы в одном контейнере, Redis один на двоих (`/0` и `/1`),
и он же с `maxmemory-policy noeviction`. Очередь генераций забивает Redis до предела →
биллинг перестаёт писать свои счётчики и сессии. Изоляция логическая, отказ общий.

**Стало:** отдельные `redis-billing` и `redis-gen` (это ничего не стоит),
отдельные роли PostgreSQL с правами только на свою базу (роль генераций физически
не может прочитать `Wallet`), и явная строчка в плане: при выручке от N ₽/мес
биллинг переезжает на отдельный managed-Postgres.

### C2. Egress без kill switch — при падении туннеля запросы уйдут с российского IP

Это не гипотетический риск: часть провайдеров закрывает доступ по гео, и уход трафика
«в открытую» — быстрый способ получить бан аккаунта, на котором лежат предоплаченные деньги.
В контейнере нет ни правил iptables, ни фиксации MTU (классические зависания
WireGuard на 1500), ни второго пира.

**Стало:** `iptables`-политика DROP по умолчанию с разрешением только через `wg0`,
`MTU 1380`, DNS исключительно через туннель, два пира с автоматическим переключением,
healthcheck, который уже есть, плюс запись в `ProviderState.egressOk` и перевод задач
в `DEFERRED`, а не в ошибку.

### C3. `worker` подключён к сети `web` без необходимости

`worker: networks: [internal, web]`. Воркеру не нужны входящие соединения и не нужна
сеть периметра — колбэки принимает кабинет. Лишняя сеть — лишний путь в обход туннеля.
**Стало:** `worker` только в `internal` и `egress_net`. Так же `bot`: Telegram доступен
исходящим из `internal`.

### C4. Запрет `setGlobalDispatcher` держится на дисциплине, а не на коде

Правило верное и важное (одна строчка в чужом модуле — и запросы к ЮKassa уходят
в туннель). Но проверить его нечем.

**Стало, три рубежа:**
1. ESLint-правило `no-restricted-imports`/`no-restricted-syntax` на `setGlobalDispatcher`.
2. Рантайм-страж: undici-интерцептор, который бросает исключение, если запрос к домену
   провайдера идёт **без** туннельного диспетчера — и наоборот, если запрос к домену кассы
   или Telegram идёт **через** туннель.
3. Тест в CI: поднять окружение, дёрнуть кассовый адаптер, убедиться, что исходящий IP не туннельный.

### C5. Нет бэкапов. Вообще

Для сервиса, где база — единственный источник истины по деньгам пользователей,
это единственный по-настоящему нерешаемый отказ. В `docker-compose.yml` нет ни дампов,
ни WAL-архива, ни версионирования бакета.

**Стало:** непрерывный архив WAL в S3 (`pgBackRest` или `wal-g`) с PITR, ежедневный
полный бэкап, **ежемесячная проверка восстановления** (бэкап без проверенного restore —
не бэкап), версионирование и lifecycle-политика на бакете, отдельный оффсайт-экземпляр
дампа биллинга.

### C6. Нет ротации логов Docker — диск кончится сам

Драйвер `json-file` по умолчанию пишет без ограничений. 160 ГБ NVMe + `LOG_LEVEL=info`
на каждом HTTP-запросе — вопрос нескольких месяцев. **Стало:** якорь `x-logging`
с `max-size: 10m, max-file: 3` на всех сервисах.

### C7. Healthcheck только у `postgres` и `egress`

`restart: unless-stopped` перезапускает упавший процесс, но не зависший.
**Стало:** `/healthz` (живость) и `/readyz` (готовность: БД, Redis, миграции) у всех
сервисов, `depends_on` с `condition: service_healthy`, `stop_grace_period` для воркера,
чтобы он успевал доработать задачу, и лимиты `deploy.resources` — иначе один сервис
съест 8 ГБ и уронит соседей.

### C8. Не описаны миграции и деплой

Prisma-схемы есть, стратегии их накатывания — нет. Кто выполняет `migrate deploy`?
Что происходит, если два инстанса стартуют одновременно?

**Стало:** одноразовый контейнер `migrator`, который выполняет миграции обеих баз
до старта приложений (`depends_on: service_completed_successfully`); правило
expand/contract (сначала добавили колонку, задеплоили код, потом удалили старую) —
без него любой релиз со сменой схемы даёт минуту 500-х.

### C9. Поллинг фиксированными интервалами и «одна очередь на всех»

`GENERATION_POLL_INTERVAL_SEC=10` для каждой задачи — это лишний трафик в туннеле
и лишняя нагрузка на провайдера. `Profile.queuePriority` в одной очереди BullMQ означает,
что тысяча бесплатных задач всё равно займёт всех воркеров.

**Стало:** экспоненциальный бэкофф поллинга (5 → 10 → 20 → 40 с, потолок 60),
поллинг только тех задач, что висят дольше трети таймаута (как и написано в §9,
но это нужно связать с полем `nextPollAt`); отдельные очереди `gen:premium`,
`gen:paid`, `gen:free` с квотой воркеров, а не общий приоритет; `jobId = generationId`,
чтобы ретрай BullMQ не порождал вторую отправку.

## Блок D. Модель данных

### D1. `Moderation.generationId @unique` не даёт записать три стадии

§14 требует три стадии модерации с записью результата в `Moderation`.
Уникальность по `generationId` разрешает ровно одну строку.
**Стало:** `@@unique([generationId, stage])`, отдельная модерация ассетов по `assetId`.

### D2. Нет модели `Asset`

`Generation.inputAssets Json` и `BrandKit.logoAssetId String? @db.Uuid` ссылаются
на несуществующую сущность. Значит: нет дедупликации загрузок, нет статуса модерации
файла, нет учёта занятого места, нет корректного каскадного удаления из S3.
**Стало:** модель `Asset` с `checksum`, `storageKey`, `mime`, `sizeBytes`, `moderationVerdict`.

### D3. Один `Output` = один файл, а нужно минимум три

`Output.storageKey` единственный. Но в продукте одновременно нужны: чистый мастер,
вотермаркнутая версия для бесплатного тарифа, миниатюра для сетки истории и превью
для соцсетей. Сейчас лента истории будет отдавать на мобильный трафик оригиналы 4K —
это и деньги за исходящий трафик S3, и мёртвый интерфейс на медленной сети.

**Стало:** `Output` (логический результат) + `OutputFile` (`kind`: `MASTER`,
`WATERMARKED`, `PREVIEW`, `THUMB`). Вотермарк — отдельный производный файл; апгрейд тарифа
открывает доступ к мастеру без перегенерации.

### D4. Политика хранения теряет файлы при смене тарифа

§16: бесплатный тариф — 7 дней. Срок считается «по текущему тарифу», значит при даунгрейде
годичный архив платного пользователя удалится следующей же ночью.
**Стало:** `Output.expiresAt` проставляется при создании и продлевается при апгрейде;
при даунгрейде — грейс-период 30 дней и письмо «скачайте или продлите».

### D5. `GuestQuota` растёт бесконечно, `AuditLog` — тоже

Ни TTL, ни партиционирования, ни задания на очистку. **Стало:** очистка гостевых квот
старше 30 дней, партиционирование `AuditLog` и `Transaction` по месяцам при росте,
индексы под фактические запросы отчётов.

### D6. Тариф BUSINESS обещает команды, а схема их не поддерживает

«команды, API-ключ, закрывающие документы» (§12) — при этом кошелёк жёстко привязан
к `User`, ролей внутри организации нет, общего баланса нет.
**Стало:** `Organization`, `OrgMember` с ролями, кошелёк, принадлежащий организации,
API-ключи с собственными лимитами и областями доступа.

### D7. Нет данных для честного ETA, хотя интерфейс его обещает

§19 требует «прогресс честный: очередь → генерация → готово, с оценкой времени».
Оценку не из чего считать: латентность моделей нигде не агрегируется.
**Стало:** `Model.p50LatencyMs` / `p90LatencyMs`, обновляемые фоновым заданием
по последним 200 успешным генерациям; ETA = позиция в очереди × средняя пропускная
способность + p50 модели.

### D8. Себестоимость в рублях хранится как `Decimal` вопреки принципу «деньги — целые»

`Generation.costRub Decimal(12,4)`. Принцип №8 требует `Int`. Разночтение приведёт
к тому, что в отчётах появятся float-преобразования.
**Стало:** `costRubKopecks Int`. `costUsd` остаётся `Decimal(10,6)` — это цена
провайдера, а не деньги пользователя, и она действительно дробная.
Отдельное правило для кодового агента: значения Prisma `Decimal` **никогда**
не приводятся к `Number` — только `.toFixed()` / целочисленная арифметика.

### D9. Курс ЦБ не публикуется по выходным и праздникам

`FxRate.date @id` + ежедневное задание = в понедельник запись за субботу отсутствует,
генерация не может зафиксировать курс. **Стало:** «последний доступный курс»
с явным полем `rateDate` в генерации (какого числа курс), fallback из `.env`,
и отдельно — понимание, что курс ЦБ ≠ реальная стоимость закупки валюты; запас
`FX_SAFETY_MARGIN_PERCENT` уже заложен, его нужно сверять с фактом ежемесячно.

## Что осталось без изменений

Не всё нужно править. Эти решения исходного ТЗ верны и в v2 сохранены дословно:

* разделение на платёжный контур и контур генераций с единственным каналом связи;
* баланс существует только в биллинге, в контуре генераций его нет;
* точечное применение прокси вместо глобального диспетчера;
* забор результата в своё S3 сразу, подписанные ссылки пользователю;
* фиксация себестоимости тремя полями (USD, курс, рубли) в момент завершения;
* неизменяемый журнал транзакций, баланс — производная;
* каталог моделей как данные, смена провайдера без деплоя;
* этапность внедрения с проверяемым критерием приёмки на каждом шаге.
