# Монетизация: как устроен денежный оборот

Механизм монетизации в предыдущих документах был разложен по трём местам —
контракт платежей в ТЗ, прайс и тарифы в продуктовом документе, поля в схеме.
Собранной картины «откуда приходит рубль и куда уходит» не было. Здесь она.

---

## 1. Схема в одном абзаце

Пользователь платит рублями за **кредиты**. Кредит — внутренняя единица,
номинально равная одному рублю. Кредиты списываются за генерации по цене,
которая в 2–5 раз выше себестоимости у провайдера. Провайдерам сервис платит
в долларах со своего предоплаченного счёта. Разница между ценой в кредитах
и себестоимостью в рублях — валовая маржа. Из неё вычитаются эквайринг, налог,
инфраструктура, партнёрские выплаты и компенсации.

```
        РУБЛИ                    КРЕДИТЫ                    ДОЛЛАРЫ
  ┌──────────────┐         ┌──────────────┐          ┌──────────────┐
  │ Пользователь │ ──────► │   Кошелёк    │ ───────► │  Провайдер   │
  │   платит     │  касса  │  (биллинг)   │ списание │  (kie.ai)    │
  └──────────────┘         └──────────────┘          └──────────────┘
     1 990 ₽                  2 400 кр                   ~6.4 USD
                                                      ≈ 624 ₽ себестоимость

  Валовая маржа: 1 990 − 624 = 1 366 ₽  (69 %)
  После эквайринга, налога и компенсаций: 1 146 ₽  (58 %)
```

Важное следствие: **выручка признаётся в момент оплаты, а себестоимость возникает
позже** — когда пользователь потратит кредиты. Между этими событиями сервис держит
обязательство. Поэтому у кредитов есть срок (12 месяцев с последней активности),
поэтому существует стоп-кран на дневной расход, и поэтому в отчётах разделены
«выручка за период» и «себестоимость за период».

## 2. Три источника выручки

| Источник | Доля на старте | Характер | Зачем нужен |
|---|---|---|---|
| **Пакеты кредитов** | ~60 % | разовая покупка | низкий порог входа, конверсия первой оплаты |
| **Подписки** | ~35 % | повторяющийся платёж | предсказуемый MRR, удержание |
| **B2B и API** | ~5 % на старте | договор, счёт, ЭДО | высокий средний чек, растёт со временем |

Пакеты и подписки **не конкурируют**: подписка даёт кредиты по лучшей цене плюс
функции (без вотермарка, приоритет очереди, рецепты), пакет — способ добрать
кредиты в пиковый месяц, не меняя тариф. Кредиты в кошельке одни и те же,
источник начисления фиксируется типом транзакции.

### 2.1 Почему кредит равен рублю

Это решение о доверии, а не об удобстве расчётов. Как только курс кредита
становится нецелым («1 кредит = 0,7 ₽»), пользователь перестаёт понимать,
сколько стоит действие, и начинает подозревать, что его обсчитывают.
При курсе 1:1 цена на кнопке «Сгенерировать · 10 кр» читается напрямую.

Скидки при этом даются **бонусными кредитами**, а не изменением курса:
курс остаётся постоянным всегда, меняется только объём в пакете.

## 3. Полный путь рубля

Каждый шаг — с указанием, где он реализован. Это ответ на вопрос
«как именно монетизация устроена в коде».

### Шаг 1. Покупка

| Что происходит | Где реализовано |
|---|---|
| Пользователь выбирает пакет или тариф | `web`, витрина из таблицы `Plan` |
| Создаётся `Payment` в статусе `PENDING` со своим `idempotencyKey` | `billing-public` |
| Формируется состав чека по 54-ФЗ и уходит в кассу | `Payment.receipt`, адаптер кассы |
| Пользователь уходит на страницу оплаты | редирект |

`providerPaymentId` в этот момент ещё пуст — он приходит из кассы,
поэтому поле nullable (дефект A8 исходного ТЗ).

### Шаг 2. Подтверждение платежа

| Что происходит | Где реализовано |
|---|---|
| Приходит вебхук, проверяются подпись и IP | `billing-public` |
| Сырое событие пишется в `PaymentWebhook` **до** обработки, с `eventKey` | защита от повтора |
| В одной транзакции БД: `Payment` → `SUCCEEDED`, `Transaction(TOPUP)`, инкремент `Wallet.credits` | `billing-internal` |
| Начисляется партнёрская комиссия в статусе «ожидает» | `PartnerCommission`, см. `09-partners.md` |
| Событие уведомления пишется в outbox | `OutboxEvent` |

Ключевое свойство: **начисление кредитов идемпотентно**. Повтор одного и того же
вебхука сто раз начислит кредиты один раз — это критерий приёмки этапа 2.

### Шаг 3. Трата

| Что происходит | Где реализовано |
|---|---|
| Проверка лимитов тарифа и стоп-крана | Redis + `SystemState` |
| Резерв кредитов: атомарный `UPDATE … WHERE credits >= N` | `POST /internal/v1/holds` |
| Генерация выполняется | `worker` |
| Успех: `Transaction(SPEND)`, `heldCredits` уменьшается | `POST /holds/:id/commit` |
| Ошибка: кредиты возвращаются целиком | `POST /holds/:id/release` |

Пользователь платит только за успешный результат — это не маркетинговое обещание,
а свойство схемы: списание физически происходит только на коммите холда.

### Шаг 4. Себестоимость

| Что происходит | Где реализовано |
|---|---|
| Фиксируется цена провайдера в USD | `Generation.costUsd` + `costSource` |
| Фиксируется курс и его дата | `fxRate`, `fxRateDate` |
| Считаются рубли в копейках | `costRubKopecks` |
| Дневной агрегат по пользователю | `UsageDaily` |
| Сверка факта с ожиданием, алерт при отклонении > 20 % | ежедневный отчёт |

Три поля вместо одного нужны, чтобы отчёт за прошлый месяц не «поплыл»
при изменении курса. Себестоимость — снимок на момент генерации, а не расчёт по факту.

### Шаг 5. Отток денег

| Статья | Величина | Где считается |
|---|---|---|
| Провайдеры | ~26 % от номинала потраченных кредитов | `Generation.costRubKopecks` |
| Эквайринг | 3–3,5 % от платежа | вычитается кассой |
| Налог УСН | 6 % от выручки | внешний учёт |
| Партнёрские выплаты | 20–30 % от выручки партнёрского канала | `PartnerCommission`, `Payout` |
| Компенсации и перегенерации | ~5 % от себестоимости | `Transaction(GOODWILL)` |
| Инфраструктура | фикс, ~4 000 ₽/мес на старте | вне системы |

## 4. Ценообразование

### 4.1 Формула

```
эффективный курс = FX_USD_RUB × (1 + FX_SAFETY_MARGIN_PERCENT/100)
priceCredits     = округление_вверх( expectedCostUsd × эффективный_курс × наценка )
```

Запас 15 % закладывается потому, что закупка идёт в валюте, а продажа в рублях,
и между ними лежит месяц: цена в кредитах меняется редко, курс — каждый день.

Наценка: **3–5× на изображениях, 2–2,5× на видео**. Разница не произвольная —
видео дороже в абсолюте, и наценка 4× сделала бы его неприемлемым по цене,
а объём генераций там на порядок ниже, так что и вклад в риск меньше.

### 4.2 Где живёт цена

Цена задаётся строкой в таблице `Model` (или `Recipe`) — **данными, не кодом**.
Провайдер поднял прайс на 30 % — правится одна строка, деплой не нужен.
Это же свойство позволяет реагировать на курс: подорожал доллар — цены в кредитах
пересматриваются массово, без релиза.

Контроль обратной связи: ежедневный отчёт сравнивает фактический `costUsd`
с `Model.expectedCostUsd`. Отклонение больше 20 % — алерт: значит цена в каталоге
устарела и маржа уже не та, что в расчётах.

## 5. Что удерживает выручку внутри

Три механики, каждая с обоснованием, — все они прямо влияют на деньги.

**Перенос остатка подписки** — не более одного месячного объёма. Даёт честную
формулировку «кредиты не сгорают, пока подписка активна» и одновременно
ограничивает накопление обязательств: без потолка через год у активного
пользователя лежит неизрасходованный полугодовой запас, который он однажды потратит разом.

**Срок жизни кредитов** — 12 месяцев с последней активности, уведомления
за 30 и 7 дней. Без срока купленные кредиты — вечное обязательство в пассиве.

**Бесплатная перегенерация** — одна в течение 10 минут при том же промпте,
не более 3 в сутки. Стоит около 5 % расхода на генерации и закрывает самую
частую претензию («получилось не то»), которая иначе приводит либо к возврату,
либо к оттоку. Это осознанно потраченная маржа, а не потеря.

## 6. Экономика на понятных числах

### 6.1 Одна покупка

Пакет 1 990 ₽ → 2 400 кредитов:

| Статья | Сумма |
|---|---|
| Выручка | 1 990 ₽ |
| Эквайринг 3,5 % | −70 ₽ |
| УСН 6 % | −119 ₽ |
| Себестоимость 2 400 кр × 0,26 ₽ | −624 ₽ |
| Компенсации ~5 % | −31 ₽ |
| **Маржинальная прибыль** | **1 146 ₽ · 58 %** |

Если покупка пришла через партнёра, считать нужно вместе с бонусом клиенту
по промокоду — он тоже стоит денег:

| | Первая покупка (промокод +10 %) | Повторные |
|---|---|---|
| без партнёра | 1 146 ₽ · 58 % | 1 146 ₽ · 58 % |
| партнёр 20 % | 683 ₽ · 34 % | 748 ₽ · 38 % |
| партнёр 30 % | 484 ₽ · 24 % | 549 ₽ · 28 % |

Даже 34 % — выгодная сделка: у партнёрского канала нет затрат на привлечение
и нет риска слить рекламный бюджет впустую. Но видно и главное: партнёрский
канал зарабатывает на повторных покупках, а не на первой. Отсюда требование
считать уровень партнёра по платящим клиентам и резать ставку тем,
кто приводит разовых покупателей (`09-partners.md §3.1`).

### 6.2 Месяц на 100 платящих клиентах

Средний чек 1 100 ₽, 30 % выручки приходит через партнёров:

| Статья | Сумма |
|---|---|
| Выручка | 110 000 ₽ |
| Провайдеры (при полном расходе кредитов) | −28 600 ₽ |
| Эквайринг | −3 850 ₽ |
| УСН 6 % | −6 600 ₽ |
| Партнёрские выплаты (33 000 × 20 %) | −6 600 ₽ |
| Бонусы по промокодам (по себестоимости) | −860 ₽ |
| Компенсации | −1 430 ₽ |
| Инфраструктура | −4 000 ₽ |
| **Прибыль до оплаты труда** | **58 060 ₽ · 53 %** |

Расчёт консервативен: он предполагает, что пользователи израсходуют **все**
купленные кредиты в том же месяце. Реально расходуется 70–80 %, но планировать
нужно по худшему — иначе неизрасходованный остаток создаёт иллюзию прибыли,
которая исчезнет, когда его потратят.

## 7. Риски модели и что их держит

| Риск | Механизм защиты |
|---|---|
| Пользователь тратит месячный бюджет за час | дневной лимит по тарифу + лимит конкурентности |
| Ошибка в коде запускает генерации в цикле | глобальный дневной потолок расходов (`SystemState`) |
| Провайдер поднял цены | ежедневная сверка факта с каталогом, алерт при 20 % |
| Курс ушёл вверх | запас 15 % в цене, ежемесячная сверка с фактической закупкой |
| Накопленные кредиты предъявят разом | потолок переноса + срок жизни + отчёт по обязательствам |
| Партнёрский фрод | комиссия подтверждается через 14 дней, см. `09-partners.md` |
| Возвраты и чарджбэки | модель `Refund`, возможность ухода баланса в минус с разбором |

## 8. Отчёты, без которых модель непрозрачна

Ежедневно, на один экран:

* выручка за сутки в разбивке: пакеты / подписки / B2B;
* себестоимость провайдеров за сутки и её доля в выручке (цель < 30 %);
* маржа по каждой модели и по каждому рецепту — что продаётся в убыток;
* обязательства: сумма неизрасходованных кредитов в рублях;
* партнёрские начисления: ожидающие подтверждения и готовые к выплате;
* воронка от визита до оплаты.

Метрика, которую смотрят первой: **доля себестоимости в выручке**. Она одна
показывает, работает ли модель, и первой реагирует на изменение цен провайдера,
на курс и на сдвиг в сторону дорогих моделей.
