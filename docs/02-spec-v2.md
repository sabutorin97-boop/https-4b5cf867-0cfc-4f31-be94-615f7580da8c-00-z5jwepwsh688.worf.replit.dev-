Документ предназначен для загрузки в кодового агента. Содержит архитектуру, контракты,

## 1. Суть проекта

Веб-сервис генерации и редактирования изображений для российского рынка.
Модели не хостим — обращаемся к внешним провайдерам через API.
Зарабатываем на разнице между себестоимостью генерации и ценой для пользователя.

Каналы: сайт (основной), Telegram-бот, позже — собственное API для B2B.
Целевая аудитория первого этапа: селлеры маркетплейсов и малые бренды —
контент для карточек товара и соцсетей.

Провайдеры: **kie.ai** (основной по изображениям), **OpenRouter** (текстовый
ИИ-консультант), **GenAPI** (резерв). Оплата провайдерам идёт со счетов владельца,
пользователь платит сервису в рублях.

**Единица ценности — не «генерация», а готовый результат под задачу.**
Пользователь покупает «фото товара на белом фоне под требования WB», а не вызов модели.
Отсюда — сущность `Recipe` (§12): пайплайн из нескольких шагов, продаваемый как один
предсказуемый по цене продукт. Это отличает сервис от обёртки над чужим API.

## 2. Принципы, которые нельзя нарушать

Эти правила важнее любых оптимизаций. При конфликте требований — выигрывают они.

1. **Баланс существует только в биллинге.** Контур генераций баланс не хранит и не считает.
2. **Ни одна генерация не запускается без подтверждённого резерва кредитов.**
3. **Каждая операция с деньгами идемпотентна.** Повтор запроса не создаёт вторую запись.
4. **Ошибка генерации возвращает кредиты автоматически.** Пользователь не платит за брак.
5. **Туннель никогда не является маршрутом по умолчанию.** Через egress ходят только
   адаптеры внешних провайдеров, всё остальное — напрямую. Правило проверяется кодом (§4.3),
   а не дисциплиной.
6. **Результат забирается в своё S3 сразу.** Ссылки провайдеров живут часы.
7. **Себестоимость фиксируется в момент завершения генерации** в полях USD, курс, копейки.
8. **Деньги — целые числа.** Копейки и кредиты в `Int`. Значения `Decimal` из Prisma
   никогда не приводятся к `Number`.
9. **Лимиты расхода проверяются до постановки задачи**, а не после.
10. **Внешний вход — источник истины только о себе.** Тело колбэка провайдера и тело
    вебхука кассы не считаются подтверждением факта; факт подтверждается нашим запросом
    к провайдеру или проверенной подписью.
11. **Ни одна операция с деньгами не выполняется чтением с последующей записью.**
    Только атомарный условный `UPDATE` (§7.2).
12. **У сервиса есть стоп-кран.** Глобальный дневной потолок расходов, срабатывающий
    без участия человека (§13.4).

## 3. Архитектура

Система делится на два контура. Падение генераций не должно останавливать приём денег.

### Платёжный контур

Прямой выход в сеть, без туннеля. Наружу ходит только в кассы.

- **web** — публичный сайт, лендинг, SEO-страницы инструментов, тарифы, оформление оплаты
- **billing-public** — вебхуки касс, SSO, публичные ручки. Доступен через Caddy.
- **billing-internal** — `/internal/v1/*`: аккаунты, баланс, холды, транзакции.
  **Не имеет маршрута из интернета** — не подключён к сети периметра.

Оба процесса биллинга — один образ и одна кодовая база, режим задаётся `BILLING_MODE`.
Разделение на два контейнера — не микросервисы, а граница доступа: внутренний API
недостижим снаружи физически, а не по договорённости.

### Контур генераций

Кабинет доступен снаружи напрямую. К провайдерам ходит только через egress.

- **app** — личный кабинет: генерации, история, проекты, консультант, приём колбэков
- **worker** — очередь генераций, ретраи, фолбэки, забор файлов в S3, деривативы
- **bot** — Telegram-бот
- **egress** — WireGuard-клиент с HTTP-прокси, слушает только во внутренней сети

### Связь между контурами

Единственный канал — внутренний API биллинга, вызываемый контуром генераций.
Обратный канал — `profile-sync` с гарантированной доставкой (§8.7).
Никаких внешних ключей между базами: `userId` в контуре генераций — обычный UUID.

```
ЮKassa / Т-Банк                                kie.ai / OpenRouter / GenAPI
      |                                                     ^
      v                                                     |
+---------------------------+                    +----------------------+
| ПЛАТЁЖНЫЙ КОНТУР          |                    | КОНТУР ГЕНЕРАЦИЙ     |
|  web (сайт, касса)        |                    |  egress (VPN+proxy)  |
|  billing-public  :3000    | <----------------- |  app (кабинет)       |
|  billing-internal :3100   |   резерв/списание  |  worker, bot         |
|                           | -----------------> |                      |
+---------------------------+   profile-sync     +----------------------+
        |                                                  |
        v                                                  v
  postgres/billing + redis-billing            postgres/generation + redis-gen
```

## 4. Инфраструктура

Хостинг: **Timeweb Cloud**, российская локация.
Первый этап — один VPS, ориентир 4 vCPU / 8 ГБ RAM / 160 ГБ NVMe.
Хранилище — S3 Timeweb, отдельным бакетом с версионированием. На диск VPS результаты не пишем.

### 4.1 Сети

| Сеть | Кто | Зачем |
|---|---|---|
| `edge` | caddy, site, cabinet, billing-public | входящие соединения из интернета |
| `internal` | все сервисы приложения, postgres, redis | межсервисное взаимодействие |
| `egress_net` | worker, egress | единственный путь к провайдерам |

`billing-internal`, `postgres`, `redis-*` не подключены к `edge` и не имеют
опубликованных портов. `worker` и `bot` не подключены к `edge` — входящих у них нет.

### 4.2 Egress

Контейнер: WireGuard-клиент + HTTP-прокси (tinyproxy), слушающий только во внутренней сети.
Требует `cap_add: NET_ADMIN`.

Обязательно:

* **Kill switch.** Правила iptables: политика `OUTPUT DROP`, разрешён только трафик
  через `wg0` плюс handshake с эндпоинтом пира. При падении туннеля запросы не уходят
  с российского IP — они не уходят вообще. Утечка = риск бана аккаунта с предоплатой.
* `MTU 1380` — иначе часть TLS-соединений виснет на больших ответах.
* DNS-резолв доменов провайдеров исключительно через туннель.
* Два пира с автопереключением по healthcheck.
* Healthcheck проверяет доступность провайдера **через прокси**, а не состояние интерфейса.
* При отказе — запись в `ProviderState.egressOk = false`; воркер переводит задачи
  в `DEFERRED`, а не в `ERROR`, кредиты остаются в холде, пользователь видит честный статус.

### 4.3 Как обеспечивается правило «туннель — не маршрут по умолчанию»

Одной строчки `setGlobalDispatcher` в чужом модуле достаточно, чтобы запросы к ЮKassa
и Telegram ушли в туннель. Поэтому правило проверяется в трёх местах:

**Рубеж 1 — линтер.** ESLint запрещает `setGlobalDispatcher` во всём монорепозитории.

**Рубеж 2 — рантайм-страж.** Единая фабрика HTTP-клиентов; прямое использование
`undici.request` вне неё запрещено линтером.

```ts
// packages/shared/src/http.ts
import { ProxyAgent, Agent, request as undiciRequest } from 'undici';

// Через туннель — только провайдеры генерации
const TUNNELED = ['api.kie.ai', 'openrouter.ai', 'api.gen-api.ru'];
// Напрямую — кассы, Telegram, S3, капча, курс ЦБ
const DIRECT = [
  'api.yookassa.ru', 'securepay.tinkoff.ru', 'api.telegram.org',
  's3.twcstorage.ru', 'smartcaptcha.yandexcloud.net', 'cbr.ru',
];

const tunnel = new ProxyAgent(process.env.EGRESS_PROXY_URL!);
const direct = new Agent({ connect: { timeout: 10_000 } });

export function httpFor(url: string) {
  const host = new URL(url).hostname;
  if (TUNNELED.some((h) => host === h || host.endsWith(`.${h}`))) return tunnel;
  if (DIRECT.some((h) => host === h || host.endsWith(`.${h}`)))   return direct;
  throw new Error(`Хост ${host} не описан в маршрутной таблице HTTP-клиента`);
}

export const httpRequest = (url: string, init: Parameters<typeof undiciRequest>[1] = {}) =>
  undiciRequest(url, { ...init, dispatcher: httpFor(url) });
```

Неизвестный хост — исключение, а не «пойдёт напрямую». Новый интеграционный домен
осознанно добавляется в таблицу.

**Рубеж 3 — тест в CI.** Поднимается окружение с мок-провайдером и мок-кассой,
проверяется фактический исходящий IP для обоих направлений.

### 4.4 Ресурсы и устойчивость

* Ротация логов Docker на всех сервисах (`max-size: 10m`, `max-file: 3`).
* `deploy.resources.limits` на каждом сервисе — один процесс не должен съесть весь RAM.
* Healthcheck `/healthz` (живость) и `/readyz` (готовность: БД, Redis, миграции)
  у всех сервисов; `depends_on: condition: service_healthy`.
* `stop_grace_period: 120s` у воркера — успеть доработать задачу.
* Миграции — одноразовым контейнером `migrator` до старта приложений.
* `security_opt: no-new-privileges`, `read_only: true` там, где возможно.

## 7. Модель данных и правила работы с деньгами

Схемы целиком — в `schema/*.prisma`. Ниже то, что нельзя вывести из схемы.

### 7.1 Инварианты

Проверяются ночным заданием, расхождение — критический алерт с остановкой начислений:

```
I1: Wallet.credits + Wallet.heldCredits == Σ Transaction.credits  (по пользователю)
I2: Wallet.heldCredits                  == Σ Hold.credits WHERE status = ACTIVE
I3: balanceAfter последней транзакции   == credits + heldCredits
I4: нет Hold в ACTIVE с expiresAt старше суток
I5: нет Generation в SUCCESS с holdId, чей Hold не в COMMITTED
```

`I1` в v1 был записан без `heldCredits` — в таком виде он ложен при любом активном
холде и давал бы ложный алерт каждую ночь.

Результат сверки пишется в `ReconciliationRun` — нужна история, а не только алерт.

### 7.2 Атомарные операции с кошельком

Никаких `SELECT` перед `UPDATE`. Резерв:

```sql
UPDATE "Wallet"
   SET credits = credits - $credits,
       "heldCredits" = "heldCredits" + $credits,
       version = version + 1,
       "updatedAt" = now()
 WHERE "userId" = $userId AND credits >= $credits
RETURNING credits, "heldCredits", version;
```

Ноль строк → `409 INSUFFICIENT_FUNDS`. Возврат резерва — зеркально.
Коммит уменьшает `heldCredits` и создаёт `Transaction(SPEND)` в той же транзакции БД.
`balanceAfter` берётся из `RETURNING`.

Порядок блокировок для операций, затрагивающих несколько кошельков
(реферальное начисление, перевод внутри организации): всегда по возрастанию `userId` —
иначе взаимоблокировка.

### 7.3 Идемпотентность

Таблица `IdempotencyRecord(scope, key, requestHash, state, statusCode, responseJson, expiresAt)`,
уникальность `(scope, key)`, TTL 30 суток.

| Ситуация | Ответ |
|---|---|
| ключа нет | вставка `IN_PROGRESS` → выполнение → `DONE` + снимок ответа |
| `DONE`, `requestHash` совпал | снимок ответа, тот же код, `Idempotent-Replay: true` |
| `IN_PROGRESS` | `409 IDEMPOTENCY_IN_PROGRESS`, `Retry-After: 1` |
| `requestHash` не совпал | `422 IDEMPOTENCY_KEY_REUSE` |

Ключи именуются с областью: `gen:{generationId}`, `topup:{paymentId}`,
`sub:{subscriptionId}:{period}`. Клиентский идентификатор принимается отдельным полем
`clientRequestId` и в ключ попадает только вместе с `userId`.
Уникальные индексы — составные: `@@unique([userId, idempotencyKey])`.

### 7.4 Единицы измерения

| Величина | Тип | Комментарий |
|---|---|---|
| деньги пользователя | `Int`, копейки | никаких дробей |
| кредиты | `Int` | 1 кредит ≈ 1 ₽ по номиналу |
| себестоимость у провайдера | `Decimal(10,6)`, USD | реально дробная |
| курс | `Decimal(10,4)` | фиксируется в генерации вместе с датой курса |
| себестоимость в рублях | `Int`, копейки | `costRubKopecks`, считается при завершении |

Даты и дневные лимиты — в `Europe/Moscow`. Ключ дневного счётчика в Redis:
`usage:{userId}:{YYYY-MM-DD}` по московской дате, TTL 48 часов.
В БД `UsageDaily.date` — та же московская дата.

## 8. Контракт внутреннего API биллинга

Базовый путь `/internal/v1`, слушает `billing-internal:3100`, только сеть `internal`.
Авторизация: `X-Service-Token` + `X-Signature` (HMAC-SHA256 от `timestamp.body`)
+ `X-Timestamp` с окном 300 секунд против повторов. Все ручки принимают `idempotencyKey`.

Единый формат ошибки:

```jsonc
{ "error": "INSUFFICIENT_FUNDS", "message": "…", "traceId": "…", "details": { } }
```

### 8.1 POST /internal/v1/holds — зарезервировать кредиты

```jsonc
// запрос
{ "userId": "uuid", "credits": 5, "idempotencyKey": "gen:<generationId>",
  "externalRef": "<generationId>", "ttlSec": 900 }

// 200
{ "holdId": "uuid", "credits": 5, "balanceAfter": 120, "expiresAt": "..." }

// 409
{ "error": "INSUFFICIENT_FUNDS", "available": 3, "required": 5 }
```

`ttlSec` вычисляется вызывающим по правилу
`model.timeoutSec * (maxAttempts + 1) + 300`, минимум 900. Сервер проверяет,
что `ttlSec` не меньше своего минимума, и отклоняет заведомо короткие резервы.

### 8.2 POST /internal/v1/holds/:holdId/commit

Создаёт `Transaction(SPEND)`, уменьшает `heldCredits`, переводит холд в `COMMITTED`.
Идемпотентен. **Холд в статусе `EXPIRED` коммитится тоже**: если средств не хватает,
создаётся списание с уходом баланса в минус, пишется `AuditLog` и алерт владельцу.
Отдать оплаченный результат и разобраться постфактум дешевле, чем раздавать генерации даром.

### 8.3 POST /internal/v1/holds/:holdId/release

Возврат резерва при ошибке, отмене, блокировке модерацией или таймауте.
Идемпотентен. На уже `COMMITTED` возвращает `409 HOLD_ALREADY_COMMITTED`.

### 8.4 GET /internal/v1/users/:userId/balance

Только для отображения. Решение о запуске генерации принимается по ответу на создание
холда, а не по этой ручке. Кэш в Redis на 5 секунд допустим — но только для витрины.

### 8.5 POST /internal/v1/grants — служебное начисление

Приветственные кредиты, компенсации, реферальные вознаграждения, начисление по подписке.
Тип транзакции передаётся явно, вызов идемпотентен, требует роли сервиса.

### 8.6 Таймауты и повторы

Если вызов завис, вызывающий повторяет запрос **с тем же ключом идемпотентности**.
Создание второго холда недопустимо. Клиент `packages/billing-client` инкапсулирует:
таймаут 5 с, 3 повтора с джиттером, обработка `409 IN_PROGRESS` как «подожди и спроси снова».
Холды с истёкшим `expiresAt` освобождаются фоновым заданием каждые 5 минут —
но только те, чья генерация уже в терминальном статусе либо старше TTL вдвое.

### 8.7 Обратный канал: profile-sync с гарантией доставки

`POST {CABINET_INTERNAL_URL}/internal/v1/profile-sync` — биллинг уведомляет кабинет
о смене тарифа. Fire-and-forget недопустим: потерянное уведомление означает, что
пользователь оплатил PRO и не получил его.

Транзакционный outbox: в одной транзакции с изменением подписки пишется `WebhookDelivery`;
отдельный воркер доставляет с ретраями (1 с, 5 с, 30 с, 5 мин, 30 мин, 2 ч),
после исчерпания — алерт. Кабинет обрабатывает идемпотентно по `deliveryId`
и игнорирует события с `version` меньше уже применённой.
Дополнительно кабинет раз в час подтягивает изменившиеся профили — сверка на случай
потери всей цепочки.

## 9. Адаптеры провайдеров

Единый интерфейс. Код приложения не знает, какой провайдер используется.
Маршрут задаётся строкой в таблице `Model`, смена провайдера не требует деплоя.

```ts
export interface GenerationRequest {
  providerModelId: string;
  prompt: string;
  params: Record<string, unknown>;
  inputFiles?: { url: string; role: string }[];
  callbackUrl?: string;
  idempotencyKey: string;
}

export interface GenerationResult {
  providerTaskId: string;
  status: 'processing' | 'success' | 'error';
  outputs?: { url: string; mimeType: string; width?: number; height?: number }[];
  costUsd?: number;
  costSource?: 'PROVIDER' | 'ESTIMATE';
  errorCode?: string;
  errorMessage?: string;
  retryable?: boolean;
}

export interface ProviderAdapter {
  readonly name: 'KIE' | 'OPENROUTER' | 'GENAPI' | 'MOCK';
  readonly supportsIdempotency: boolean;
  submit(req: GenerationRequest): Promise<GenerationResult>;
  poll(providerTaskId: string): Promise<GenerationResult>;
  findByIdempotencyKey?(key: string): Promise<GenerationResult | null>;
  parseCallback(body: unknown, headers: Record<string, string>): GenerationResult;
  getBalance(): Promise<{ balanceUsd: number } | null>;
}
```

Требования:

* все запросы идут через `httpFor()` (§4.3), напрямую `undici` — нельзя;
* таймаут из `Model.timeoutSec`;
* **`submit` не ретраится вслепую.** Сетевой таймаут ≠ «задача не создана»; чаще наоборот.
  При обрыве генерация переходит в `SUBMIT_UNKNOWN` и попадает в реконсиляцию:
  `findByIdempotencyKey` там, где провайдер это умеет, иначе ожидание колбэка
  до истечения `timeoutSec`. Повторная отправка разрешена только после подтверждения,
  что задачи у провайдера нет. Цена нарушения — двойная оплата провайдеру;
* `poll` и `getBalance` ретраятся на сетевых ошибках и 5xx: максимум 2 повтора,
  экспоненциальная пауза с джиттером;
* 4xx не ретраится — задача сразу в `ERROR` с возвратом кредитов;
* себестоимость пишется из ответа провайдера с `costSource = PROVIDER`;
  если провайдер не отдаёт — `Model.expectedCostUsd` и `costSource = ESTIMATE`;
* каждый адаптер имеет контрактный тест против записанных фикстур ответов.

### 9.1 Колбэки провайдеров

Приходят на публичный домен кабинета, туннель для входящих не нужен.

* URL содержит одноразовый токен: `/api/callbacks/{provider}/{generationId}/{token}`,
  `token = HMAC(CALLBACK_SECRET, generationId)`, сравнение константное по времени.
* Подпись провайдера проверяется там, где она есть.
* Сырое событие пишется в `ProviderCallback` **до** обработки; обработчик отвечает 200
  за миллисекунды и ставит задачу в очередь.
* **Тело колбэка не источник истины.** Факт успеха и `costUsd` подтверждаются
  вызовом `poll`. Колбэк — сигнал «пора спросить», не более.
* Автомат статусов монотонный: назад не переходим, дубли и опоздавшие события отбрасываются.
* Параллельно работает поллинг задач, висящих в `PROCESSING` дольше трети таймаута,
  с бэкоффом 5 → 10 → 20 → 40 → 60 с через поле `nextPollAt`.

### 9.2 Забор результата

Результаты отдаются с CDN провайдера, чей домен заранее неизвестен, поэтому
маршрутная таблица §4.3 здесь неприменима: забор файла использует туннельный
диспетчер **явно**, отдельной функцией `downloadThroughTunnel()`. Это единственное
разрешённое исключение из правила «хост должен быть в таблице», и оно компенсируется
проверкой адреса ниже.

Скачивание идёт через egress со строгой проверкой URL:
только `https`; резолв имени и проверка **итогового** IP против приватных диапазонов
(RFC1918, loopback, link-local, CGNAT, IPv6 ULA); не более 3 редиректов с повторной
проверкой на каждом; лимит размера и времени; сверка `Content-Type`.
Иначе провайдер (или подделанный колбэк) заставит воркер сходить во внутреннюю сеть.

После скачивания sharp формирует деривативы: `MASTER` (перекодирован, EXIF снят),
`WATERMARKED` (для бесплатного тарифа), `PREVIEW` 1280px, `THUMB` 320/640 в AVIF.
В ленту истории и в мобильный интерфейс отдаются только миниатюры.

## 10. Жизненный цикл генерации

```
1.  Кабинет принимает запрос, валидирует Zod, применяет модерацию промпта
2.  Проверка лимитов (Redis: дневной расход, конкурентность, рейт-лимит)
3.  Проверка SystemState (стоп-кран) и ProviderState (доступность, баланс, egress)
4.  Создание Generation в PENDING с серверным idempotencyKey и callbackToken
5.  POST /holds → holdId  (при 409 — экран «пополнить», задача не ставится)
6.  Постановка в очередь по классу тарифа, jobId = generationId
7.  Worker: submit через egress → PROCESSING
8.  Колбэк или поллинг → подтверждение через poll
9a. Успех: файл в S3, деривативы, costRubKopecks, /commit, SUCCESS
9b. Ошибка: фолбэк на Model.fallbackProvider — дочерняя Generation
    НАСЛЕДУЕТ holdId родителя, второй резерв не создаётся
9c. Фолбэк не помог: /release, ERROR, кредиты у пользователя
10. Уведомление через outbox: SSE в интерфейс, Telegram, если аккаунт связан
```

Статусы: `PENDING → QUEUED → PROCESSING → SUCCESS | ERROR | CANCELED`,
плюс `BLOCKED` (модерация), `DEFERRED` (egress недоступен), `SUBMIT_UNKNOWN` (см. §9).

При отказе egress задачи не ретраятся вхолостую: `DEFERRED`, кредиты остаются в холде,
пользователь видит «сервис временно недоступен, кредиты не списаны». Холд продлевается,
пока задача в `DEFERRED`; если недоступность длится дольше 30 минут — `release`
и предложение повторить позже.

### 10.1 Очереди

Три очереди вместо приоритета в общей: `gen:premium`, `gen:paid`, `gen:free`,
с фиксированной долей воркеров (например 3 / 4 / 1). Тысяча бесплатных задач
не должна задерживать оплаченную. Плюс per-user семафор в Redis по
`Profile.concurrentJobs`. `jobId = generationId` — ретрай BullMQ не порождает
второй отправки.

### 10.2 Честный ETA

`Model.p50LatencyMs` и `p90LatencyMs` пересчитываются фоновым заданием по последним
200 успешным генерациям. Оценка = позиция в очереди / пропускная способность + p50.
Пользователю показывается диапазон, а не точка. Если превысили p90 — интерфейс честно
пишет «дольше обычного», а не крутит бесконечный спиннер.

## 11. Платежи

Провайдеры: ЮKassa и Т-Банк (СБП), отдельные адаптеры за общим интерфейсом.

1. Пользователь выбирает пакет кредитов или тариф.
2. Создаётся `Payment` в `PENDING` со своим `idempotencyKey`; `providerPaymentId`
   ещё пуст — он приходит из кассы (поэтому поле nullable).
3. Обращение в кассу с **составом чека** по 54-ФЗ (§5 в `05-legal-ru.md`) —
   без него платёж принимать нельзя.
4. Редирект на страницу оплаты.
5. Вебхук.

Обработка вебхука строго в этом порядке:

1. Проверка подписи и IP отправителя (список сетей — в `.env`).
2. Запись сырого события в `PaymentWebhook` **до** обработки, с `eventKey`
   (идентификатор события провайдера либо `sha256(body)`) — уникальность
   `(provider, eventKey)`. В v1 ключ был nullable, и защита не работала:
   в PostgreSQL два `NULL` не конфликтуют.
3. Проверка `providerPaymentId` на уникальность и допустимости перехода статуса.
4. В одной транзакции БД: обновление `Payment`, создание `Transaction(TOPUP)`,
   атомарный инкремент `Wallet.credits`, запись в outbox уведомления.
5. Ответ 200.

Упал после шага 2 — событие переигрывается фоновым заданием из `PaymentWebhook`.
Событий без соответствующего `Payment` не бывает: если пришло — алерт, не игнор.

**Возвраты.** Отдельная модель `Refund` с `providerRefundId`, суммой и причиной:
частичные возвраты неизбежны, а `Payment.refundedAt` их не выражает.
Возврат списывает кредиты обратно; если кредиты уже потрачены — баланс уходит в минус,
запись в `AuditLog`, ручной разбор.

**Подписки.** Автопродление фоновым заданием по `Subscription.currentPeriodEnd`,
списание сохранённым методом. Неудача → `PAST_DUE`, три попытки (сутки, трое суток,
неделя), затем `EXPIRED` и понижение до бесплатного тарифа с грейс-периодом
на хранение файлов (§16). Уведомления перед каждым списанием — требование
и закона, и здравого смысла.

## 12. Тарифы, кредиты и рецепты

Кредит — внутренняя единица, **номинально 1 кредит = 1 ₽**. Это осознанное решение:
пользователь должен мгновенно понимать цену, а не пересчитывать «попугаев».

Расчёт цены модели:

```
priceCredits = ceil( expectedCostUsd × fxRate × (1 + FX_SAFETY_MARGIN) × markup )
```

Целевая наценка: 3–5× на массовых моделях, 2–2,5× на видео. Округление вверх
до «человеческих» значений (5, 10, 15, 25, 40), а не до 7 или 13.

### 12.1 Рецепты — то, что на самом деле покупают

`Recipe` — именованный пайплайн из шагов, каждый шаг ссылается на `Model`.
Пример «Карточка для WB»: удаление фона → подстановка сцены → апскейл →
кадрирование под 900×1200.

Пользователь видит один результат и одну цену. Цена рецепта — сумма шагов плюс
наценка за упаковку. Резерв кредитов делается **один раз на весь рецепт**
(`PipelineRun`), холд общий; провал любого шага возвращает весь резерв.
Промежуточные результаты не показываются, если шаг не помечен `visible`.

Это ключевое отличие от обёртки над API: продаётся результат под конкретную площадку,
а не абстрактный вызов модели. Подробнее — `04-product.md`.

### 12.2 Стартовая сетка

Задаётся данными, не кодом.

| Тариф | Цена | Кредитов/мес | Что даёт |
|---|---|---|---|
| FREE | 0 | 10 при регистрации | вотермарк, низкое разрешение, только дешёвые модели, хранение 7 дней |
| START | 690 ₽ | 800 | без вотермарка, полное разрешение, хранение бессрочно |
| PRO | 1 490 ₽ | 2 000 | приоритет очереди, пакетный режим, премиум-модели, брендкит, рецепты |
| BUSINESS | от 9 900 ₽ | 15 000 | команды, общий кошелёк, API-ключ, закрывающие документы, ЭДО |

Пакеты кредитов: 299 / 799 / 1 990 ₽ с бонусом (+0 % / +12 % / +20 %) —
бонус, а не скидка: он не обесценивает базовую цену.
Перенос неизрасходованных кредитов подписки — до одного месячного объёма.
Обоснование и экономика — `04-product.md`.

## 13. Лимиты и защита бюджета

Владелец оплачивает провайдеров вперёд, поэтому защита обязательна в первой версии.

### 13.1 Лимиты пользователя

Счётчики в Redis, дневной итог в `UsageDaily`:
дневной потолок расхода по тарифу, конкурентные задачи (`Profile.concurrentJobs`),
рейт-лимит на постановку задач и на сообщения консультанту.
Проверка — **до** создания холда.

### 13.2 Гости

Схема v1 (2 генерации по отпечатку браузера) обходится инкогнито-окном.
Послойная защита:

1. Yandex SmartCaptcha перед первой гостевой генерацией.
2. Квота по отпечатку **и** по IP **и** по подсети /24 **и** по ASN.
3. Только самая дешёвая модель, низкое разрешение, вотермарк.
4. Глобальный дневной потолок расходов на гостей в USD; при исчерпании гостевой
   режим отключается автоматически до следующих суток.
5. Результат гостя сохраняется 24 часа и **привязывается к аккаунту при регистрации** —
   это и защита, и главный конверсионный крючок (§4 в `04-product.md`).
6. Очистка `GuestQuota` старше 30 дней.

### 13.3 Контроль провайдеров

Фоновое задание раз в 10 минут опрашивает балансы, пишет в `ProviderState`
(с кэшем в Redis — читать таблицу на каждый запрос не нужно).
Ниже `PROVIDER_BALANCE_WARN_USD` — уведомление владельцу в Telegram;
ниже `PROVIDER_BALANCE_STOP_USD` — переключение на резервного;
все недоступны — мягкое отключение платных генераций с внятным сообщением
и сохранением кредитов.

### 13.4 Стоп-кран

Таблица `SystemState` — единственное место, откуда всё выключается:

| Флаг | Что делает |
|---|---|
| `dailyBudgetUsd` / `dailySpentUsd` | превышение → платные генерации останавливаются |
| `guestModeEnabled` | гостевой режим |
| `paidGenerationsEnabled` | аварийная остановка |
| `signupsEnabled` | защита от волны ботов |
| `maintenanceMessage` | текст для интерфейса |

Проверка — до постановки задачи, значения кэшируются в Redis на 10 секунд.
Срабатывание стоп-крана не требует деплоя и не требует человека ночью.

### 13.5 Контроль маржи

Ежедневный отчёт сравнивает фактический `costUsd` с `Model.expectedCostUsd`.
Отклонение больше 20 % — алерт: провайдер изменил цены, цена в кредитах устарела.
Отдельно — доля себестоимости в выручке за сутки; целевой порог указан
в `06-marketing.md`, превышение — тоже алерт.

## 14. Модерация

Три стадии, результат в `Moderation` с уникальностью `(generationId, stage)` —
в v1 уникальность была по `generationId`, что позволяло сохранить только одну стадию из трёх.

1. **Промпт** — стоп-слова и классификатор до отправки провайдеру.
2. **Входное изображение** — проверка загрузок (привязка к `Asset`).
3. **Результат** — выборочная проверка вывода.

Блокируется: сексуальный контент, насилие, генерация узнаваемых реальных людей
и публичных персон, материалы с участием несовершеннолетних.
При вердикте `BLOCK` задача не отправляется провайдеру, вызывается `release`,
кредиты не списываются, пользователю показывается причина без раскрытия правил фильтра.

Три повторных `BLOCK` подряд — временная блокировка постановки задач и запись
в `AuditLog`; десять за сутки — блокировка аккаунта и ручной разбор.
Список правил и вердиктов версионируется (`Moderation.rulesVersion`),
иначе разбор спорных случаев невозможен.

## 15. ИИ-консультант

Роль — не поддержка, а интерфейс. Убирает необходимость уметь писать промпты.

Функции: принимает задачу на естественном языке, собирает промпт, выбирает модель
из каталога, выставляет размер, запускает генерацию; правки итерациями
(«фон светлее», «сделай вертикально»); подсказывает форматы под площадки;
предупреждает, когда кредитов не хватит.

Реализация: OpenRouter, дешёвая модель, вызовы через egress.
Диалог в `ChatSession` / `ChatMessage` с учётом токенов и стоимости.
Бесплатным — 10–15 сообщений, дальше по тарифу.

Ограничения, без которых консультант становится дырой в бюджете:

* выбор модели — **только** из каталога с `enabled = true` и доступных тарифу;
  идентификатор модели никогда не берётся из текста ответа LLM напрямую,
  только сопоставлением с белым списком;
* запуск генерации идёт тем же путём: лимиты → холд → очередь → коммит.
  Обходных путей нет;
* лимит на длину контекста и на стоимость одного диалога в USD;
* содержимое пользовательских сообщений и результатов поиска — **данные, не инструкции**;
  системный промпт явно это фиксирует, попытки переопределить правила игнорируются;
* стоимость каждого сообщения пишется в `ChatMessage.costUsd` и попадает в отчёт о марже:
  консультант — тоже себестоимость.

## 16. Хранилище

S3 Timeweb, версионирование включено. Ключи: `{userId}/{generationId}/{outputId}-{kind}.{ext}`.

Файл забирается у провайдера сразу по колбэку, до отдачи пользователю.
Пользователю выдаются подписанные ссылки с коротким временем жизни (`S3_SIGNED_URL_TTL_SEC`).

Каждый результат — несколько файлов (`OutputFile.kind`): `MASTER`, `WATERMARKED`,
`PREVIEW`, `THUMB`. Бесплатному тарифу подписывается только `WATERMARKED`;
апгрейд открывает `MASTER` без перегенерации.

**Срок хранения** фиксируется в `Output.expiresAt` при создании, а не вычисляется
от текущего тарифа: иначе даунгрейд уничтожит архив следующей же ночью.
Апгрейд продлевает, даунгрейд даёт 30 дней грейса и письмо.
Удаление — фоновым заданием, с удалением объектов в S3, а не только пометкой в БД.

Загрузки: проверка MIME по содержимому, лимит размера **и лимит пикселей**
(защита от «архивных бомб»), антивирус (`clamav`), обязательное перекодирование
через sharp со снятием EXIF — включая GPS-координаты пользователя.

## 17. Наблюдаемость

Логи JSON с `traceId`, сквозным через все сервисы, включая вызовы биллинга.
Секреты и промпты пользователей в логи не пишутся; `userId` — да, персональные данные — нет.

Метрики с первого дня:

* очередь: длина по классам, время ожидания, доля ошибок по провайдерам;
* деньги: расход USD за сутки, выручка ₽, маржа по моделям, доля себестоимости;
* провайдеры: балансы, латентность p50/p90, статус egress;
* воронка: регистрации, первая генерация, первая оплата, время до первого успеха.

**Транзакционный outbox.** Уведомления (SSE, Telegram, письма) пишутся в `OutboxEvent`
в одной транзакции с бизнес-изменением и доставляются отдельным воркером.
Иначе «коммит прошёл, уведомление потерялось» — и пользователь не знает, что готово.
SSE между несколькими инстансами кабинета — через Redis pub/sub; в Caddy для этого
маршрута отключается буферизация.

Алерты владельцу в Telegram: падение egress, низкий баланс провайдера, доля ошибок
выше 10 % за 15 минут, расхождение инвариантов при ночной сверке, неудачная обработка
вебхука кассы, срабатывание стоп-крана, отклонение себестоимости больше 20 %.
У каждого алерта — ссылка на runbook (`07-operations.md`).

## 18. Безопасность

* Внутренний API биллинга физически недостижим из интернета (§3): отдельный контейнер
  без подключения к сети периметра. Одного `X-Service-Token` между интернетом
  и балансами пользователей быть не должно.
* Подпись межсервисных запросов с меткой времени и окном против повторов;
  плановая ротация `SERVICE_TOKEN`, поддержка двух активных ключей на время ротации.
* Вебхуки касс: подпись + список IP + `eventKey` (§11).
* Колбэки провайдеров: токен в URL + подпись + подтверждение поллингом (§9.1).
* Забор файлов: защита от SSRF (§9.2).
* Валидация всех внешних входов через Zod, включая тела вебхуков.
* Пароли — argon2id; API-ключи — только хэш; **refresh-токены — тоже только хэш**
  (в v1 хранились открыто, что при утечке дампа означало захват всех сессий);
  ротация refresh-токена при каждом обновлении, инвалидация цепочки при повторном
  использовании старого.
* JWT: RS256 или Ed25519, приватный ключ только в биллинге; в `.env` — base64,
  чтобы многострочный PEM не ломал парсинг.
* Секреты только в переменных окружения (в перспективе — docker secrets),
  в репозитории — `.env.example`. Секреты не логируются и не попадают в Sentry.
* Rate limiting на периметре (Caddy) плюс прикладной по `userId`.
* Заголовки безопасности, HSTS, CSP на кабинете; cookie `HttpOnly`, `Secure`, `SameSite=Lax`.
* Роли PostgreSQL: биллинг-роль не имеет прав на базу генераций и наоборот.

## 19. Экраны

Полная спецификация — `03-design.md`. Здесь только рамка.

**Публичный сайт (`web`):** главная с полем промпта и пресетами, страницы инструментов
под SEO (по одной на задачу, программно генерируемые), тарифы, оплата, оферта
и политика, публичная галерея с opt-in и модерацией.

**Кабинет (`app`):** рабочая зона генерации, чат с консультантом, история и избранное,
проекты и брендкит, рецепты, пакетный режим, баланс и тариф, реферальная ссылка, API-ключи.

Дизайн: тёмная тема по умолчанию, один акцентный цвет, без градиентов.
Стоимость в кредитах и рублях показывается **до** запуска.
Прогресс честный: очередь → генерация → готово, с диапазоном времени из `p50/p90`.
Мобильная версия обязательна и проектируется первой.

## 20. Этапы

Каждый этап заканчивается проверяемым автотестом, а не «работает у меня».

**Этап 1 — каркас.** Docker Compose, egress с kill switch, две базы и две роли,
биллинг с холдами и транзакциями, адаптер kie.ai, mock-провайдер, одна модель,
генерация из кабинета, бэкапы с проверенным восстановлением.
*Приёмка:* E2E-тест — полный цикл генерации; выключение туннеля на середине
задачи приводит к `DEFERRED`, а затем к автоматическому возврату кредитов;
ночная сверка инвариантов на сгенерированных данных проходит.

**Этап 2 — деньги.** ЮKassa и Т-Банк, вебхуки с идемпотентностью и `eventKey`,
чеки 54-ФЗ, пакеты и тарифы, лимиты и гостевые квоты с капчей, стоп-кран,
ночная сверка в проде.
*Приёмка:* повтор одного и того же вебхука 100 раз начисляет кредиты один раз;
параллельные 50 запросов на резерв не уводят баланс в минус.

**Этап 3 — продукт.** Каталог моделей с фолбэками, рецепты, пресеты, история и S3
с деривативами, модерация, консультант на OpenRouter.
*Приёмка:* фолбэк не создаёт второго холда; пользователь с балансом ровно
в цену модели успешно проходит через фолбэк.

**Этап 4 — каналы.** Telegram-бот со сквозным балансом, SEO-страницы инструментов,
реферальная программа с антифродом, публичная галерея.

**Этап 5 — B2B.** Организации и команды, пакетный режим, брендкит, API-ключи
с лимитами, закрывающие документы и ЭДО.

## 21. Что запрещено делать

* Дублировать баланс в контуре генераций.
* Использовать `setGlobalDispatcher` или заворачивать весь трафик в туннель.
* Обращаться к внешним хостам мимо `packages/shared/http`.
* Запускать генерацию до подтверждения резерва.
* Создавать второй холд на фолбэк.
* Ретраить `submit` к провайдеру после сетевого таймаута без реконсиляции.
* Читать баланс и затем его записывать — только атомарный условный `UPDATE`.
* Доверять телу колбэка провайдера как подтверждению успеха и стоимости.
* Отдавать пользователю прямые ссылки провайдеров.
* Скачивать файл по URL из внешнего источника без проверки на приватные адреса.
* Хранить результаты на диске VPS.
* Начислять кредиты по вебхуку без проверки подписи и уникальности события.
* Хранить refresh-токены в открытом виде.
* Использовать числа с плавающей точкой для денег и кредитов; приводить `Decimal` к `Number`.
* Создавать внешние ключи между базами двух контуров.
* Публиковать наружу `/internal/*` любым способом, включая «временно, для отладки».

## 22. Тестовая стратегия

Без неё критерии приёмки этапов непроверяемы.

| Уровень | Что покрывает | Инструмент |
|---|---|---|
| Модульные | расчёт цены, округление, конвертация валют, парсеры ответов провайдеров | vitest |
| Свойства | инварианты кошелька при случайной последовательности операций | fast-check |
| Контрактные | внутренний API биллинга — со стороны сервера и клиента | vitest + фикстуры |
| Адаптеры | записанные ответы провайдеров, включая ошибки и таймауты | nock/undici mock |
| Конкурентность | 50 параллельных резервов, повторные вебхуки, гонка commit/expire | testcontainers |
| E2E | полный цикл на mock-провайдере, отказ egress, отказ биллинга | Playwright |
| Нагрузка | профиль очереди на пиковую нагрузку, деградация под лимитами | k6 |

Обязательный элемент — **mock-провайдер** как отдельный сервис в compose
(профиль `dev`): управляемые задержки, ошибки, «зависшие» задачи, дубли колбэков.
Проверить сценарии отказа на живом kie.ai нельзя, а именно они определяют,
теряет ли сервис деньги.

CI на каждый PR: типы, линт (включая запрет `setGlobalDispatcher`), модульные,
контрактные, миграции на чистой базе. E2E — на ветке перед релизом.
